How to use

Ion Engine, start to shipped ad

A practical walkthrough of the tools you'll actually touch — the UI Editor, the Engine Room panel, and Control Desk — plus the Ion facade for writing gameplay code, from npm run dev to a self-contained dist/index.html. Not an architecture reference and not a setup manual — those live in ENGINE.md and README.md. This is "it's running, now what do I click."

The three tools

UI Editor
Design the HUD/endcard — text, images, buttons, progress bars, sliders, sprites, the joystick and more. Opens as a live overlay on the running game.
Engine Room
The dev panel itself — Build, 3D View, Audio Reactor, FPS/stats. Always visible, docked right.
Control Desk
Live-tweak gameplay numbers and booleans while the game is actually running.

This page is the tour. Each system has its own page with the full API and copy-paste examples.

1

Start it up

npm install
npm run dev

Open the URL it prints — usually http://127.0.0.1:8000. The game runs full-screen with the dark Engine Room panel docked on the right. Everything in that panel only exists in this dev preview; none of it ships in the real playable.

2

Design a screen

Click ✏️ Editor at the top of Engine Room. It opens on top of the running game — you're editing live, not in a separate preview.

  1. ＋ Insert (or I) opens the palette — text, rects, buttons, groups, progress bars, sliders, toggles, checkboxes, shapes, icons, sprites, video, the joystick. Images come in through the 🖼️ button beside it.
  2. Drag to position — it snaps to other elements and to guides. Eight handles resize, the grip above rotates. Properties (right) is sectioned: layout and anchoring, fill (solid or gradient), typography, animation, hover/pressed states, and click actions.
  3. Layers (left) lists everything, with a filter, collapsible groups, and per-row lock and visibility. The Assets and Prefabs tabs beside it hold reusable images and saved selections.
  4. Watch the ✅ badge in the toolbar — it flags duplicate names, missing image sources, zero-size elements and dead action targets before they become a broken ad.
  5. Save writes straight to mainLayout.json (or the endcard layout) — no file picker. The button turns green with a ✓, and the running game hot-reloads immediately.
Everything placed here becomes a named element game code can reach directly — which is exactly what the next step is for. Buttons can also act on their own: show, hide and setText actions need no code at all. Press ? in the editor for every shortcut.
3

Wire an element to code

Example: a text element named moneyIcon that HUD.ts should control directly.

  1. In the UI Editor, open Scripts (below Layers) — only files under */ui/*.ts show up, since those are the classes with UI-assignable fields.
  2. Pick a script. Its public fields appear; an unassigned one still reads undefined.
  3. Drag the element from Layers onto the field — or click ⊙ Pick next to the field, then click the element on the canvas (more reliable across panels than drag-and-drop).

No code to write — the field is populated automatically via applyBindings(...), called once in that class's own constructor. Toggle 🐞 Debug here to also see private fields — dimmed, read-only, for visibility only.

4

Tune gameplay live

For actual gameplay values — speed, a counter, anything public on a running game object — not layout.

  1. In Engine Room, scroll to 📜 Scripts — a different list from the editor's: everything under src/game/ except ui/ (that's step 3's job).
  2. Click a script, e.g. entities/Player.ts. 🕹 Control Desk shows every public field live: number → editable input, boolean → checkbox, arrays → a read-only dropdown, everything else → read-only text.
  3. A live badge means an instance is actually running — a field is only editable once it is.

🐞 Debug also reveals private/protected fields (dimmed, read-only). 💾 Save writes your tweak straight back into the .ts source as the field's new default, so it survives the next reload instead of resetting — the dev watcher picks up the change and hot-reloads automatically.

Grouping fields with Header()

// Header("Player settings")
public speed: number = 5;

Everything below that comment — down to the next Header(...) or the end of the class — shows grouped under a "Player settings" divider in Control Desk. Add as many as you want, wherever you want; it's read straight from source, no registration step.

5

Debug audio

Click 🎧 Audio Reactor (below 3D View in Engine Room) to open a live frequency-spectrum bar graph of whatever background music is actually playing — confirms a track is really running, not just "should be," and gives you something to eyeball while tuning levels.

  • The status dot reads Playing (green, pulsing) or Stopped — tap the game to start music — browsers block audio until a real tap, click, or keypress happens, so this is usually the first sign something's wrong if music won't start.
  • The bar graph and the level readout (e.g. 42 / 255) only animate while music is actually playing — a flat line with the panel open means nothing's loaded, or nothing's unlocked audio yet.
Dev-only readout, same as 3D View and Control Desk — nothing here ships in the real playable.
6

Inspect and edit the 3D scene

Click 🧭 3D Viewer/Editor at the top of Engine Room. It orbits the actual running scene, not a separate preview, so what you click is what's really there. Two docks flank the viewport: left is Hierarchy (top) + Scripts (bottom); right is Exit, a camera-orientation compass, Inspector, and Control Desk.

Hierarchy

  • Only the top level starts expanded — click ▸ to open a branch, ▾ to close it. A GLB-heavy scene can be hundreds of objects; this keeps it browsable.
  • Click a row to select it. Selection is shared everywhere — viewport, Inspector, Control Desk all update together.
  • Press . any time to jump back to whatever's currently selected — opens whatever was collapsed to reveal it, with a quick flash.
  • Drag a row out and drop it on a Control Desk field to assign it (see below).

Inspector

  • Name — with a 📋 button to copy it.
  • Parent — click it to jump to the parent object instead.
  • Vertices / Triangles — shown for a mesh.
  • 👁 Visible — click the eye to show/hide. Slashed eye = hidden.
  • Position / Rotation / Scale — real inputs; type a value or drag the gizmo in the viewport, both stay in sync.

Assign a scene object to a script field

Example: Player.ts has public popcornMachine!: THREE.Object3D;

  1. Click entities/Player.ts in the Scripts list (left).
  2. Control Desk shows a ⊙ Pick button next to popcornMachine automatically — any field typed as an Object3D/Mesh/Group/light/camera gets one.
  3. Click ⊙ Pick then click the object — in the Hierarchy or the viewport, either works — or skip Pick and drag the row straight out of the Hierarchy onto the field.
  4. Click ✕ Exit Editor — that's the actual save. It shows how many are pending, e.g. ✕ Exit & Save (1).

Saved assignments survive every reload from then on — written to src/game/sceneBindings.json, re-applied automatically on every boot.

A class that needs the object inside its own constructor (not just later, in update()) has to populate it itself — same reason and same pattern as HUD.ts's applyBindings call. See the code reference below for applySceneBindings.
7

Write gameplay code with Ion

Everything above is the visual tools. This is for timed beats, tweens, and cross-system events in code — without hand-rolling timers or holding direct references between classes.

// import { Ion, Easing } from "../engine/Ion";

Ion.after(3, () => hud.showHook());                    // once, 3s from now
Ion.every(0.5, () => spawner.tick());                   // repeating
Ion.sequence([                                          // back-to-back beats
  { wait: 0.5, then: () => coin.pop() },
  { wait: 0.2, then: () => hud.bumpScore() },
]);
Ion.tween(mesh.scale, { x: 1.4, y: 1.4, z: 1.4 }, 0.25, { easing: Easing.Back.Out });

Ion.on("coin-collected", (p) => hud.setScore(p.total)); // subscribe
Ion.emit("coin-collected", { total: 5 });                // fire, from anywhere else

Ion.cta(STORE_URL);                                       // a CTA button's click handler
  • Everything on Ion runs on game time, not wall-clock — it pauses automatically while the UI editor or 3D View is open, and resumes exactly where it left off. No extra code needed.
  • Call Ion.* from a constructor, update(), or an event handler — not a file's top-level module code. Ion only exists once IonEngine.boot() has actually created a game; calling it too early throws a clear error saying exactly that.
  • Ion.on/Ion.emit don't need event names declared anywhere — use the same string on both sides. Type the payload at the call site if you want it checked: Ion.on<{total: number}>("coin-collected", fn).

Animate anything with Animator

Ion.tween moves a target's own fields toward a value directly. Animator is for when you want the raw 0→1 progress number yourself — driving two properties together, a custom formula, anything that isn't "move these fields to this value."

// import { Animator } from "../engine/core/Animator";
// import { Easing } from "../engine/Ion";

// progress goes 0 -> 1 over 0.5s, eased with Back.Out
new Animator({ time: 0.5, easing: Easing.Back.Out }, (progress) => {
  mesh.scale.setScalar(progress);
});

// delay is optional; no easing = plain linear; 3rd arg (optional)
// fires once, right when progress hits 1
new Animator({ time: 1, delay: 0.3 }, (progress) => {
  door.rotation.y = progress * Math.PI;
}, () => console.log("door fully open"));

Self-driving, same as Ion.tween — construct it and move on, nothing to call every frame yourself.

Movement input has a desktop fallback too: WASD or arrow keys move the player alongside the joystick automatically — no setup, useful for testing at a desk without touching the canvas.

Full API and reasoning: ENGINE.md's Ion.ts / core/Scheduler.ts / core/Animator.ts / core/EventBus.ts / core/InputManager.ts sections.

8

Ship it

🛠 Builder (top of Engine Room) runs build.sh: compresses every model and audio asset, bundles src/main.ts with Vite (vite-plugin-singlefile), inlines that JS directly into src/index.template.html, then base64-inlines every real asset straight into that same file — one genuinely self-contained dist/index.html, no dist/assets/ folder, nothing else to upload. Opens directly via file:// and works on any ad network that only accepts a single file, including the exact syntax and module checks Mintegral's Mindworks review enforces — checked automatically on every build, not just at submission time. Nothing from the Engine Room panel itself ships in the output; the production template never references any of it.

✓ on Half Float mesh compression — extra size reduction at no visual cost
🚀 Build Now — runs the real build
📊 Build Report — size breakdown, per-asset compression, ad-network warnings
Build Report flags a red banner if the output still contains anything ad-network review would reject — check it before uploading anywhere. It also lists any file sitting unused in assets/ that never got referenced, and the exact before/after size of every model and audio file that did.

If gameplay ever throws an unhandled error mid-session in the shipped build, players see a minimal "Continue" screen with a working install button instead of a dead frame — the ad spend isn't a total loss even if something breaks. Nothing to configure; it's automatic.

bash build.sh

Engine code reference

Steps 1–8 above are the panels and clicks. This is the rest of src/engine/ — every reusable class a new playable actually imports, each with the exact signature and a minimal real example. Ion/Animator already got a full walkthrough in step 7; everything below is what's left.

Boot

src/main.ts does this and nothing else — don't add to it, add to Game.ts instead.

// src/main.ts
import { IonEngine } from "./engine/IonEngine";

const canvas = document.getElementById("game") as HTMLCanvasElement;
IonEngine.boot(canvas);

Optional second argument: { fixedTimestep: 1/60 } — opts into a fixed-step accumulator instead of variable dt. Turn it on only if you're integrating forces or resolving collisions, where a frame spike needs to run several fixed steps instead of one big one.

Wiring scene objects to fields — SceneBindings.ts

The code-side half of step 6's ⊙ Pick/drag-and-drop — resolves every saved assignment for a class and writes the real object onto the field.

// import { applySceneBindings, type SceneBindingsData } from "../../engine/SceneBindings";
// import sceneBindingsRaw from "../sceneBindings.json";

constructor(scene: THREE.Scene) {
  applySceneBindings(this, "Player", sceneBindingsRaw as SceneBindingsData, scene);
  // this.popcornMachine is populated from here on
}

Game.ts also re-applies it to every class registered in its inspectables map automatically — but only after every constructor has already run. Call it yourself, like above, if a constructor needs the field immediately.

Wiring UI elements to fields — Bindings.ts

Same idea, for elements placed in the UI Editor instead of scene objects — the code-side half of step 3.

// import { applyBindings, type BindingsData } from "../engine/Bindings";
// import bindingsRaw from "./bindings.json";

constructor() {
  applyBindings(this, "HUD", bindingsRaw as BindingsData, this.main, this.endcard);
  // this.moneyIcon (etc.) is populated from here on
}

Reading and driving a designed layout — UILayout.ts

Every UILayout instance (this.mainUI, this.endcardUI in Game.ts) exposes the same handful of runtime methods, regardless of which layout JSON built it:

get(name)
Look up a placed element's node by the name you gave it in the editor.
setText(name, text)
Update a text element's content at runtime.
setImage(name, src)
Swap an image element's source (a dynamic badge/icon).
show(name) / hide(name)
Toggle one element's own visibility.
setVisible(bool)
Show/hide every element this layout placed, as one group.
setInteractive(nameOrEl, onClick?)
Opt an element into receiving clicks — sets pointer-events + cursor, wires the handler.
getJoystick(name)
Returns { base, knob } for a "joystick"-type element, to wire real input to it.
this.ui.setText("scoreLabel", `${this.collected} / ${this.total}`);
this.ui.setInteractive("ctaButton", () => Cta.open(STORE_URL));

Input — InputManager.ts

Generic tap/swipe/drag + the keyboard-axis fallback (WASD/arrows) — independent of the joystick, for anything the joystick was never meant to cover.

const input = new InputManager(window, () => hud.hideDragHint());  // target, onFirstInput

input.onTap(({ x, y }) => tryPickUp(x, y));
input.onSwipe(({ dx, dy, angle }) => dodge(angle));

// combine with the joystick — joystick wins whenever it's actively held
const axis = joystick.axis.x || joystick.axis.y ? joystick.axis : input.keyboardAxis;

input.setEnabled(false) suspends it — the 3D Editor does this for its own session, since its W/E/R/Q gizmo shortcuts collide with WASD on the same window keydown listener.

The joystick — DynamicJoystick.ts

this.input = new DynamicJoystick(
  this.mainLayer,       // parent element
  joystick.base,        // designed base node, from UILayout.getJoystick()
  joystick.knob,        // designed knob node
  45,                    // radius, px
  () => this.soundHandler.playMusic()  // onFirstInput
);

// every frame:
this.player.update(dt, elapsed, this.input.axis);  // { x, y }, both -1..1

Gameplay camera — CameraHandler.ts

this.cameraHandler = new CameraHandler(this.camera, new THREE.Vector3(0, 12, 12)); // camera, offset

// every frame:
this.cameraHandler.update(this.player.position, dt); // smoothly follows

// on resize:
this.cameraHandler.handleResize(width, height);

Loading assets — AssetLoader.ts

Preloads everything up front behind one await — a playable can't afford a stutter the first time an asset is needed mid-gameplay, so nothing loads lazily.

const loader = new AssetLoader();
await loader.preload(manifest, (loaded, total) => updateBar(loaded / total));

const model = loader.getGlb(libGlb.player).scene;     // already resolved, sync
const clips = loader.getAnimations(libGlb.player);
const buffer = loader.getAudio(libAudio.MainMusic);
const tex = loader.getTexture(libTex.coin);

manifest is a plain array of { kind: "glb"|"audio"|"texture", path } — see game/assets.ts's libGlb/libAudio/libTex namespaces for the pattern this game's own manifest follows.

Adding a new gameplay object — the Entity contract

The minimum shape Game.ts needs to treat something uniformly — not a base class to extend, just an interface to satisfy:

interface Entity {
  readonly object3D: THREE.Object3D;
  update(dt: number, elapsed: number): void;
  dispose?(): void;  // optional — for anything spawned/despawned at runtime
}

Deliberately minimal — a class with extra per-frame inputs (Player needs the joystick axis, for example) just widens its own update() signature. This is a floor, not a framework.

Routing the install click — Cta.ts

One call, regardless of which ad network's SDK actually rendered the playable — never call window.open() or a network's API directly.

this.hud.onCtaClick(() => Cta.open(STORE_URL));

Checks Mindworks, Facebook, IronSource, MRAID, in that priority order, then falls back to a plain browser window.open — exactly one handler ever fires.

Surviving a crash — CrashOverlay.ts

// once, near the top of Game.ts
setCrashRecoveryUrl(STORE_URL);

That's the only call site needed — if gameplay throws mid-session, the engine's own crash guard (see IonEngine.ts) shows a minimal "Continue" screen wired to this URL automatically. The ad spend isn't a total loss even if something breaks.
