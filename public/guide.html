Ion Engine TECHNOLOGY Guide

How to use

Ion Engine, start to shipped ad

A practical walkthrough of the tools you'll actually touch — the UI Editor, the Engine Room panel, and Control Desk — plus the Ion facade for writing gameplay code, from npm run dev to a self-contained dist/index.html. Not an architecture reference and not a setup manual — those live in ENGINE.md and README.md. This is "it's running, now what do I click."

The three tools

UI Editor
Design the HUD/endcard — buttons, text, images, the joystick. Opens as a live overlay on the running game.
Engine Room
The dev panel itself — Build, 3D View, Audio Reactor, FPS/stats. Always visible, docked right.
Control Desk
Live-tweak gameplay numbers and booleans while the game is actually running.
1

Start it up

npm install
npm run dev

Open the URL it prints — usually http://127.0.0.1:8000. The game runs full-screen with the dark Engine Room panel docked on the right. Everything in that panel only exists in this dev preview; none of it ships in the real playable.

2

Design a screen

Click ✏️ Editor at the top of Engine Room. It opens on top of the running game — you're editing live, not in a separate preview.

  1. Along the top: Image / Text / Rect / Joystick / Group — click one to drop it onto the canvas.
  2. Click an element to select it. Properties (right) shows everything about it — X/Y with a per-axis PX / % toggle, the 3×3 anchor grid, a ⊙ Center (0, 0) quick-reset, width/height, rotation, opacity, and — for text — a color picker and 3-way align control.
  3. Layers (left) lists everything on the canvas. Drag to reorder, drag one row onto another to group, click the eye icon to hide.
  4. Save writes straight to mainLayout.json (or the endcard layout) — no file picker. The running game hot-reloads immediately.
Everything placed here becomes a named element game code can reach directly — which is exactly what the next step is for.
3

Wire an element to code

Example: a text element named moneyIcon that HUD.ts should control directly.

  1. In the UI Editor, open Scripts (below Layers) — only files under */ui/*.ts show up, since those are the classes with UI-assignable fields.
  2. Pick a script. Its public fields appear; an unassigned one still reads undefined.
  3. Drag the element from Layers onto the field — or click ⊙ Pick next to the field, then click the element on the canvas (more reliable across panels than drag-and-drop).

No code to write — the field is populated automatically via applyBindings(...), called once in that class's own constructor. Toggle 🐞 Debug here to also see private fields — dimmed, read-only, for visibility only.

4

Tune gameplay live

For actual gameplay values — speed, a counter, anything public on a running game object — not layout.

  1. In Engine Room, scroll to 📜 Scripts — a different list from the editor's: everything under src/game/ except ui/ (that's step 3's job).
  2. Click a script, e.g. entities/Player.ts. 🕹 Control Desk shows every public field live: number → editable input, boolean → checkbox, arrays → a read-only dropdown, everything else → read-only text.
  3. A live badge means an instance is actually running — a field is only editable once it is.

🐞 Debug also reveals private/protected fields (dimmed, read-only). 💾 Save writes your tweak straight back into the .ts source as the field's new default, so it survives the next reload instead of resetting — the dev watcher picks up the change and hot-reloads automatically.

Grouping fields with Header()

// Header("Player settings")
public speed: number = 5;

Everything below that comment — down to the next Header(...) or the end of the class — shows grouped under a "Player settings" divider in Control Desk. Add as many as you want, wherever you want; it's read straight from source, no registration step.

5

Debug audio

Click 🎧 Audio Reactor (below 3D View in Engine Room) to open a live frequency-spectrum bar graph of whatever background music is actually playing — confirms a track is really running, not just "should be," and gives you something to eyeball while tuning levels.

  • The status dot reads Playing (green, pulsing) or Stopped — tap the game to start music — browsers block audio until a real tap, click, or keypress happens, so this is usually the first sign something's wrong if music won't start.
  • The bar graph and the level readout (e.g. 42 / 255) only animate while music is actually playing — a flat line with the panel open means nothing's loaded, or nothing's unlocked audio yet.
Dev-only readout, same as 3D View and Control Desk — nothing here ships in the real playable.
6

Write gameplay code with Ion

Everything above is the visual tools. This is for timed beats, tweens, and cross-system events in code — without hand-rolling timers or holding direct references between classes.

// import { Ion, Easing } from "../engine/Ion";

Ion.after(3, () => hud.showHook());                    // once, 3s from now
Ion.every(0.5, () => spawner.tick());                   // repeating
Ion.sequence([                                          // back-to-back beats
  { wait: 0.5, then: () => coin.pop() },
  { wait: 0.2, then: () => hud.bumpScore() },
]);
Ion.tween(mesh.scale, { x: 1.4, y: 1.4, z: 1.4 }, 0.25, { easing: Easing.Back.Out });

Ion.on("coin-collected", (p) => hud.setScore(p.total)); // subscribe
Ion.emit("coin-collected", { total: 5 });                // fire, from anywhere else

Ion.cta(STORE_URL);                                       // a CTA button's click handler
  • Everything on Ion runs on game time, not wall-clock — it pauses automatically while the UI editor or 3D View is open, and resumes exactly where it left off. No extra code needed.
  • Call Ion.* from a constructor, update(), or an event handler — not a file's top-level module code. Ion only exists once IonEngine.boot() has actually created a game; calling it too early throws a clear error saying exactly that.
  • Ion.on/Ion.emit don't need event names declared anywhere — use the same string on both sides. Type the payload at the call site if you want it checked: Ion.on<{total: number}>("coin-collected", fn).
Movement input has a desktop fallback too: WASD or arrow keys move the player alongside the joystick automatically — no setup, useful for testing at a desk without touching the canvas.

Full API and reasoning: ENGINE.md's Ion.ts / core/Scheduler.ts / core/EventBus.ts / core/InputManager.ts sections.

7

Inspect the 3D scene

Click 🧭 3D View to freecam the live scene, click any object to select it, and drag the Move/Rotate/Scale gizmo to edit it live. A second toolbar cluster adds five more toggles:

Grid — G
A ground-reference grid, off by default.
Helpers — H
Camera frustum + light helper visibility, on by default.
Snap — X
Fixed increments on the active gizmo instead of freehand.
Space — C
Toggles the gizmo between local and world orientation.
Frame — F
Snaps the camera to fit whatever's currently selected.

Dev-only, same as everything else in this section — none of it ships in the production build.

8

Ship it

🛠 Builder (top of Engine Room) runs build.sh: compresses every model and audio asset, bundles src/main.ts with Vite (vite-plugin-singlefile), inlines that JS directly into src/index.template.html, then base64-inlines every real asset straight into that same file — one genuinely self-contained dist/index.html, no dist/assets/ folder, nothing else to upload. Opens directly via file:// and works on any ad network that only accepts a single file, including the exact syntax and module checks Mintegral's Mindworks review enforces — checked automatically on every build, not just at submission time. Nothing from the Engine Room panel itself ships in the output; the production template never references any of it.

✓ on Half Float mesh compression — extra size reduction at no visual cost
🚀 Build Now — runs the real build
📊 Build Report — size breakdown, per-asset compression, ad-network warnings
Build Report flags a red banner if the output still contains anything ad-network review would reject — check it before uploading anywhere. It also lists any file sitting unused in assets/ that never got referenced, and the exact before/after size of every model and audio file that did.

If gameplay ever throws an unhandled error mid-session in the shipped build, players see a minimal "Continue" screen with a working install button instead of a dead frame — the ad spend isn't a total loss even if something breaks. Nothing to configure; it's automatic.

bash build.sh
